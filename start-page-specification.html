Product & technical specification

Start

A self-hosted, identity-aware dashboard for discovering internal tools and resources. The product gives users a fast, personalized directory while allowing delegated administrators to safely maintain links for the groups and categories they own.

1. Summary

Start is a responsive web application that an organization can run on its own network. It stores and presents links to existing services such as Stirling PDF; it does not install, bootstrap, monitor, proxy, or manage those services.

Find quickly

Browse categories, switch to a flat view, or fuzzy-search titles, descriptions, URLs, and tags.

See what matters

Filter by identity roles and teams, then let each user hide links that are irrelevant to them.

Delegate safely

System, group, and category administrators manage only their authorized scope, with protected deletion.

Success measures

  • A signed-in user can reach a known tool from the home screen in under 10 seconds.
  • Search feedback appears within 100 ms for a typical directory of up to 5,000 links.
  • Routine link maintenance does not require filesystem, YAML, or database access.
  • Unauthorized links and management actions are never disclosed by API responses.
  • A new instance can start from a single container and persistent SQLite volume.

2. Scope

In scope for v1

  • OIDC sign-in through Tinyauth, with Pocket ID as the supported upstream identity provider.
  • Identity claim mapping for stable user ID, email, display name, roles, teams, and groups.
  • Link, category, group, tag, visibility-rule, and delegated-administrator management.
  • Categorized and flat browsing, fuzzy search, keyboard navigation, and personal hiding.
  • Dark, light, Hacker, and 1984 themes; custom name, logo, colors, and welcome text.
  • SQLite persistence, one-time YAML seed, Goose SQL migrations, and sqlc-generated data access.
  • Health/readiness endpoints, Prometheus metrics, structured logging, and branded error pages.
  • Container image, example Compose deployment, and documented backup/restore.

Explicitly out of scope for v1

  • Installing or controlling linked services, including Stirling PDF.
  • Checking availability of every link or promising that a link is safe.
  • A secrets vault, password manager, reverse proxy, or identity provider.
  • Public anonymous access, native mobile apps, browser extensions, or internet-wide crawling.
  • Full boolean policy language, link approval workflows, link analytics, favorites, or manual ordering.
  • The VPN/network heuristic beyond reserving a header component and API contract.
Deployment assumption: Start runs as a container behind an HTTPS reverse proxy at an operator-selected hostname. The application remains responsible for its own OIDC session and authorization checks.

5. UX specification

Primary page structure

  1. Header: branding, reserved network-status area, administration/settings actions, and a user menu labeled Welcome <OIDC name>.
  2. Toolbar: the search field is the first main-page control, followed by the categorized/flat toggle and add-link action when authorized. Do not repeat welcome copy, branding text, or destination counts above it.
  3. Content: responsive link-card grid grouped by category, or one flat ranked result grid.
  4. Footer: version/build information and optional operator-defined support link.

Link card

  • Icon, title, hostname, optional description, and tags. Cards use a real anchor so open-in-new-tab, copy-link, and accessibility semantics work normally.
  • Actions appear in a keyboard-reachable overflow menu: open, copy URL, hide/show, edit, and delete when permitted.
  • Links open in the same tab by default. A per-user setting may change this to a new tab; new-tab links include rel="noopener noreferrer".
  • Hidden links appear with reduced emphasis only while “Show hidden” is enabled.

Search behavior

  • Search is client-side over the already authorized payload, debounced no more than 75 ms. Matching is case-insensitive, diacritic-insensitive, and tolerant of minor typos.
  • Ranking weights: title 5, tags 4, hostname 3, description 2, URL path 1; prefix matches receive a bonus.
  • The URL bar may encode ?q= and ?view= so a view can be bookmarked without storing identity data in the URL.
  • If the query is non-empty and exactly one result remains, show “Press Enter to open.” Never trigger this shortcut while a dialog, menu, or form control owns keyboard focus.

Keyboard-first navigation and hotkeys

Every primary workflow must work with the keyboard alone, and the hotkey layer is enabled by default. Pressing ? opens a searchable shortcut reference that lists only actions available to the current user. Interactive elements retain normal Tab behavior, a visible focus indicator, logical focus order, and native activation semantics.

Forms and dialogs

Dialogs trap focus, close on Escape unless a save is in progress, restore focus to their trigger, and expose a visible title. Unsaved forms warn before closing. Cards use a single column below 560 px, two columns when space permits, and an auto-fitted grid on larger displays. The header collapses into a compact toolbar without hiding search. All actions remain available by keyboard and touch at a minimum 44 × 44 px target size.

6. Authentication and authorization

Recommended identity flow

Browser→Start→Tinyauth OIDC→Pocket ID→Passkey / identity

The Go application is an OIDC confidential client using Authorization Code flow. It discovers Tinyauth from its issuer metadata, requests openid profile email groups, validates issuer, audience, signature, expiry, nonce, and state, then creates an opaque application session. Tinyauth may use Pocket ID upstream. This keeps the application standards-based and avoids trusting identity headers from arbitrary clients.

Identity key: store users by (issuer, subject). Email can change and is not a safe primary key. Keep normalized email as a display/contact attribute and optional lookup key.

Claim mapping

Local attributeDefault claimBehavior
IssuerConfigured Tinyauth issuer / token issRequired and matched exactly to the discovered issuer.
SubjectsubRequired, combined with issuer; never user-editable.
EmailemailRequired by the target Tinyauth configuration; normalized for display and admin search.
Display namename, fallback preferred_username, then emailRefreshed from profile claims.
Identity groupsgroupsString array supplied by Pocket ID through Tinyauth; refreshed and used as the sole IdP input to authorization mappings.
RolesDatabase mapping from groupsAn explicit mapping associates an exact IdP group value with a Start role slug. Unmapped groups grant nothing.
TeamsDatabase mapping from groupsAn explicit mapping associates an exact IdP group value with a Start team slug. Unmapped groups grant nothing.
Administrative grantsLocal user grant or mapping from groupsMay grant system, owner-group, or category administration. Email domains never grant authority.

A supported deployment configures Pocket ID as Tinyauth’s upstream provider with openid email profile groups and configures Tinyauth as an OIDC issuer. Start therefore consumes the standard claims above; it does not depend on separate roles or teams claims.

Visibility rule

A link is included when it is enabled and each populated audience dimension matches:

visible = link.enabled
  AND (link.roles is empty OR user.roles intersects link.roles)
  AND (link.teams is empty OR user.teams intersects link.teams)
  AND (show_hidden OR link.id not in user.hidden_links)

This gives OR behavior within a dimension and AND behavior between roles and teams. An empty role and team set means “all authenticated users.” The rule is evaluated in SQL or server code before serialization; the Vue app never receives unauthorized links.

Mutation authorization

can_manage(link, user) = user.is_system_admin
  OR link.owner_group_id in user.admin_group_ids
  OR link.category_id in user.admin_category_ids
  • Creating a link requires system-admin status or administration of the selected owner group. Category administration alone cannot create a link.
  • Changing owner group requires administration of both the old and new groups, or system-admin status.
  • Changing category requires authorization for the resulting link under the same rule; category admins cannot use reassignment to escape their scope.
  • Every create, update, delete, category/group change, and admin assignment is audit logged.

Administrative grant sources and precedence

  • Local grants: a system admin can grant a known OIDC identity a system, owner-group, or category administration capability in SQLite.
  • IdP grants: a system admin can map an exact value from the OIDC groups claim to the same capabilities and scopes.
  • Effective authority: the union of active local grants and mappings matched by the user’s current IdP groups. v1 has no deny rules.
  • Membership changes: IdP-derived grants are not copied into permanent user grants. They disappear when the group is absent at the next claim refresh. The default maximum claim age is 15 minutes; an administrative mutation requires claims no older than 5 minutes and triggers refresh or reauthentication when stale.
  • Every authorization decision is made by Start’s server-side policy layer using the effective grants. Tinyauth authenticates the person and supplies groups; it does not decide Start’s record-level permissions.

Session policy

  • Opaque, random session ID in a Secure, HttpOnly, SameSite=Lax cookie; rotate after login.
  • Idle lifetime default 8 hours; absolute lifetime default 24 hours; both configurable.
  • Server-side session revocation on logout. Logout then navigates through Tinyauth’s trusted logout route, which performs Pocket ID RP-initiated logout using Tinyauth’s Pocket ID ID-token hint before returning to Start. Redirect targets must be relative or on an explicit allowlist.
  • CSRF protection for all state-changing requests using same-origin checks plus a CSRF token.

Reference: Tinyauth’s Pocket ID guide and Tinyauth OIDC server guide.

7. System architecture

Backend

  • Go current stable release, Gin HTTP framework.
  • Layered modular monolith: HTTP handlers → services/policy → sqlc repositories.
  • OIDC client and server-side sessions.
  • SQLite driver with context cancellation and bound parameters.
  • Embedded Vue production assets using go:embed.

Frontend

  • Vue 3 Composition API + TypeScript + Vite.
  • Pinia for session/preferences/admin state; Vue Router for routes.
  • Local fuzzy-search index built only from authorized links.
  • CSS custom properties for themes and branding.
  • Bundled icon subsets; no runtime CDN requirement.

Bazel build and developer workflow

  • Use MODULE.bazel (Bzlmod), MODULE.bazel.lock, a pinned .bazelversion, and checked-in BUILD.bazel files. Do not introduce a legacy WORKSPACE dependency graph.
  • Use rules_go for Go build/test/cross-compilation and Gazelle to maintain Go targets from go.mod. go.mod remains the Go dependency source of truth.
  • Use aspect_rules_js with a frozen pnpm-lock.yaml to run the Vue/Vite build, TypeScript checks, linting, component tests, and development server through Bazel targets.
  • Provide bazel run //:dev as the single-command local launch path. It builds the backend and production frontend assets, enables the explicit development identity, seeds an empty SQLite database, and serves on loopback by default.
  • Use rules_oci to assemble the non-root production image from the Go binary, embedded frontend assets, certificates, and migration metadata, and to produce linux/amd64 and linux/arm64 images.
  • Run sqlc through bazel run //tools:sqlc_generate. Generated Go files are checked in; bazel test //tools:sqlc_generated_check regenerates in a sandbox and fails on a diff.
  • Embed Goose SQL migrations in the Go binary. bazel test //db/migrations:verify applies them to a temporary SQLite database, validates forward migration, and exercises supported down migrations.
  • Build metadata such as version, commit, and build time is injected through declared Bazel stamping only for release builds; ordinary builds remain cacheable and reproducible.

Runtime topology

Reverse proxy / HTTPS→Go + Gin API and embedded Vue SPA→SQLite volume

A single application process is the default. SQLite runs in WAL mode with foreign keys enabled and a bounded busy timeout. A read-only filesystem is supported except for the database, temporary runtime directory, and optional uploaded branding directory. Horizontal multi-writer scaling is not supported in v1; operators needing it should move to a future database backend.

Integrity and deletion

  • Enable PRAGMA foreign_keys = ON on every connection.
  • Categories and groups referenced by links use ON DELETE RESTRICT; joins use appropriate cascade deletion only during an explicit maintenance purge.
  • Link deletion is a recoverable soft delete after confirmation and authorization. It sets deleted_at and writes a delete revision in the same transaction.
  • Restoring any historical snapshot writes its fields back to the current link, clears deleted_at when appropriate, and appends a new restore revision. Revision rows are never edited in place.
  • All timestamps are UTC RFC 3339 at boundaries and integer/time types internally.
  • Writes that affect link plus tags/audience rules run in one transaction.

10. links.yaml seeding

On startup after migrations, the application checks for application data in one transaction. If categories, groups, and links are all empty and a configured seed file exists, it validates the entire document and imports it atomically. Invalid input fails readiness with actionable line/path errors. If any application data exists, the seed file is ignored and a structured informational event is logged.

version: 1
categories:
  - slug: development
    name: Development
    color: "#3b82f6"
    order: 10
groups:
  - slug: platform
    name: Platform
links:
  - slug: stirling-pdf
    title: Stirling PDF
    url: https://pdf.internal.example
    description: Internal PDF toolbox
    category: development
    ownerGroup: platform
    icon:
      provider: material
      name: picture_as_pdf
      color: "#ef4444"
    tags: [pdf, documents]
    audience:
      roles: []
      teams: []
  • version is mandatory and unsupported versions are rejected.
  • Slugs are stable lowercase identifiers matching [a-z0-9][a-z0-9-]{0,62}.
  • References must resolve within the file. Duplicate slugs, malformed colors, invalid icons, and disallowed URL schemes reject the entire seed.
  • The seed does not assign administrators by email. Initial system admins come from configured identity-group mapping.
  • An explicit CLI command and system-admin web dialog support merge imports. Both leave omitted records unchanged; startup never merges automatically.

Configuration is validated before serving traffic. Secrets are never printed. Environment variables override a non-secret configuration file; command-line flags are limited to operational commands such as serve, migrate, and version.

Deployment automation contract

Environment-specific deployment automation should remain declarative rather than relying on one-off shell steps:

  • Define the Start hostname, target hosts, image reference, trusted proxies, and bootstrap administrator group in private inventory variables.
  • Add the hostname to authoritative DNS and grant the certificate updater permission for its ACME challenge records before requesting the certificate.
  • Declare a Tinyauth OIDC client named start with display name Start, stable client credentials, and trusted redirect URI https://start.example.com/auth/callback.
  • Generate the Start client ID/secret once, store them in a secret manager, and render them into both Tinyauth and Start without logging them. Re-running automation must not rotate credentials unintentionally.
  • Manage the Pocket ID start-admins group declaratively through its authenticated API. Look up by exact group name, create only when missing, and converge an optional authoritative username list when configured.
  • Add a Start service playbook for its persistent database directory, environment/secret files, container, systemd unit, reverse-proxy hostname, readiness validation, and backup path.
  • Do not add Start to Tinyauth’s forward-auth tinyauth_apps list. Start is itself an OIDC client; wrapping it in forward-auth would create two independent authentication layers.
  • Apply in dependency order: Pocket ID group → Tinyauth OIDC client/credentials → Start deployment → readiness and OIDC smoke test.

12. Operations and observability

Health

  • /healthz returns process liveness with no identity or dependency details.
  • /readyz fails until configuration, migrations, database read/write test, seed decision, and asset availability succeed.
  • Destination links are not part of application readiness.

Metrics

  • Request count and duration by method, normalized route, and status class.
  • Active sessions; login success/failure; database operation duration/error count; seed outcome.
  • Link create/update/delete/restore counts and authorization denials, without link URLs, queries, email addresses, or subjects as labels.
  • Go runtime/process metrics. Keep metric labels bounded to prevent cardinality growth.

Structured request logging

Emit JSON in production with timestamp, level, request ID, trace ID when available, method, normalized route, status, duration, response bytes, client IP only when policy permits, and a one-way actor reference for authenticated actions. Never log cookies, tokens, secrets, raw query text, full URLs submitted as links, or complete error stacks to clients.

Audit and revision retention

  • Retain audit events for 365 days by default, configurable by duration. A daily maintenance task purges expired audit events in bounded batches.
  • Retain link revisions indefinitely by default. No normal v1 UI action permanently purges a link or its revision history.
  • Revision restore remains link-scoped even when submitted as a batch: the administrator selects exactly which links to restore, each selected snapshot creates a new head revision, and the transaction changes no unselected links. This supports selectively moving several links back without a database-wide rollback.
  • A future operator-only purge command may remove revisions after backup, but it is not required for v1.

Backups and recovery

  • Document SQLite online backup or VACUUM INTO procedures; do not copy a live WAL database as one file.
  • Back up database, uploaded branding assets, and operator configuration. The seed is not a backup after initialization.
  • Before migration, create a verified backup unless the operator explicitly disables it.
  • Provide a startup check and documented restore drill.

Error pages

Browser pages use current branding, a plain explanation, safe next action, and request ID. The 404 page offers Home and Search. The 403 page does not reveal whether a hidden resource exists. The 5xx page does not expose stack traces or internal paths.

13. Security requirements

  • Validate OIDC metadata and tokens with a maintained library; require exact issuer and expected audience/client ID.
  • Use authorization code flow, PKCE where supported, random state and nonce, short callback lifetime, and replay protection.
  • Enforce server-side visibility and mutation policy on every request. Do not treat hidden UI controls as authorization.
  • Use bound SQL parameters, transactional writes, and explicit allowlists for sortable/filterable column names.
  • Allow HTTP, HTTPS, and other well-formed destination schemes globally. Reject browser-executable javascript:, data:, and vbscript: schemes plus embedded credentials, because rendering those as links would cross the application’s code-execution or credential-leak boundary.
  • Escape all text. Descriptions and branding text are plain text in v1; no arbitrary HTML or SVG uploads.
  • If logo upload is enabled, decode and re-encode supported raster formats, enforce size/dimensions, generate a random filename, and serve with a fixed safe content type.
  • Set Content-Security-Policy, frame-ancestors, nosniff, strict referrer policy, and HSTS when HTTPS termination is correctly detected.
  • Bundle fonts/icons/assets locally by default so the dashboard works without internet access and does not leak browsing metadata.
  • Rate-limit login initiation/callback errors and mutations; cap body sizes and field lengths.
  • Trust forwarded headers only from configured proxies. Reject inconsistent host/origin values.
  • Record administrative actions in an append-only audit trail, with a configurable retention policy.
  • Run as non-root with a read-only root filesystem, minimal container image, pinned dependencies, and automated vulnerability scanning.
Boundary: visibility rules personalize and conceal directory entries; they do not authorize the linked applications. Every destination service must enforce its own authentication and authorization, commonly through Tinyauth/Pocket ID or native OIDC.

15. Verification strategy

Backend

  • Table-driven unit tests for visibility and management policy matrices.
  • OIDC callback tests for invalid issuer, audience, signature, nonce, state, expiry, and missing claims.
  • Repository integration tests against temporary SQLite with migrations applied.
  • Seed tests for empty/non-empty databases, atomic failure, references, and version handling.
  • Grant-source tests for local and OIDC-group authority, claim-age enforcement, group removal, and scoped capability unions.
  • Revision tests proving create/update/delete/restore snapshots are immutable, ordered, transactional, and restorable in either direction.
  • HTTP contract tests covering status codes, JSON errors, CSRF, concurrency conflicts, and information leakage.

Frontend and end-to-end

  • Component tests for cards, toggles, form validation, icon fallbacks, and dialogs.
  • Search ranking, diacritics, typo tolerance, single-result Enter, focus guards, empty queries, the complete hotkey map, and shortcut-disable preference.
  • End-to-end role matrix for user, group admin, category admin, and system admin.
  • Mobile/desktop visual regression for all four themes and custom branding.
  • Automated accessibility checks plus manual keyboard and screen-reader smoke tests.

Release gates

  • bazel test //..., the applicable Go race-test target, static analysis, frontend typecheck/lint/tests, sqlc generated-code check, migration verification, and production image build pass.
  • Fresh install, upgrade from previous schema, backup/restore, and rollback documentation are exercised.
  • No critical/high known vulnerabilities without a written, time-bounded exception.
  • Acceptance criteria below pass in an environment using Tinyauth with Pocket ID upstream.

17. v1 acceptance criteria

  1. Given a logged-out browser, visiting the app starts OIDC login and returns to the original safe relative path after successful Tinyauth/Pocket ID authentication.
  2. Given identity roles/teams, the bootstrap and link APIs return exactly the links allowed by the documented visibility expression.
  3. Given a query matching title, description, URL, or tag, results update and rank predictably; Enter opens only when one result remains or a result is explicitly selected.
  4. Using only a keyboard from the loaded dashboard, a user can discover shortcuts, focus and clear search, move through links, open a link, toggle views, hide/restore a link, operate menus and dialogs, and complete permitted create/edit workflows. Single-character shortcuts do not fire while typing and can be disabled.
  5. A user can switch categorized/flat view, hide and restore a link, change every display preference, reload, and observe the same state.
  6. The same identity opening a second browser receives preferences from SQLite; local storage accelerates startup but does not attach preferences to a different identity.
  7. Local and OIDC-group grants combine as documented. Removing a user from a mapped Pocket ID group removes the derived authority after claim refresh without deleting any separate local grant.
  8. A group admin can maintain links in their groups but receives 403 for another group. A category admin can edit links in their category but can create only when they also administer the selected owner group. A system admin can manage all records.
  9. Deleting a link requires a named confirmation, returns a useful conflict if the record changed, soft-deletes transactionally, and writes both an audit event and immutable revision. The global admin history shows every manageable link change; an admin can select historical snapshots for three links, restore them atomically, and observe that all unselected links remain unchanged.
  10. Dark, Light, Hacker, and 1984 themes render at mobile and desktop sizes with WCAG AA contrast for normal controls and text.
  11. When a valid links.yaml exists and the database is empty, it imports once. Restart preserves UI edits. Invalid seed data imports nothing and fails readiness clearly.
  12. Devicon, Font Awesome, and Material choices render offline; an unknown icon falls back to a stable monogram or generic link symbol without broken-image UI.
  13. Liveness, readiness, metrics policy, structured request logs, request IDs, branded errors, and the custom 404 behave as specified without exposing secrets or personal data.
  14. The documented container deployment works on amd64 and arm64 with a persistent SQLite volume and a successful backup/restore exercise.
  15. From a clean checkout with Bazelisk but no separately installed Go, Node, pnpm, sqlc, or Goose tools, the documented Bazel targets build the binary/frontend/image, run all tests, and verify generated SQL code and migrations reproducibly.
  16. The documented deployment automation converges idempotently, preserves existing OIDC credentials, creates the start-admins Pocket ID group when absent, and completes an authenticated readiness smoke test.

18. Recorded decisions and open items

Recorded for this draft

  • Product name: the product and default browser title are Start; “internal start page” remains the descriptive category.
  • Canonical deployment: Start is served as a container behind an operator-managed HTTPS reverse proxy.
  • Build system: Bazel with Bzlmod is the canonical build/test/codegen/image interface, using rules_go + Gazelle, aspect_rules_js + pnpm, and rules_oci.
  • Tinyauth spelling and role: Tinyauth is the OIDC-facing authentication service; Pocket ID may be its upstream provider.
  • Target claims: the identity deployment supplies sub, email, profile/name, and groups through Tinyauth. Roles, teams, and administrative grants derive from explicit mappings of exact groups values.
  • Stable identity: preferences and admin assignments key to OIDC issuer + subject, not email.
  • Ownership vs visibility: owner groups govern maintenance; roles and teams govern personalization.
  • Category creation: category administration alone does not permit creation; the creator must administer the selected owner group.
  • Audience semantics: OR within roles/teams, AND across the two populated dimensions.
  • Grant sources: effective administrative authority is the union of local user grants and current mapped IdP-group grants.
  • Database evolution: Goose SQL migration files apply schema changes; sqlc.yml configures type-safe query generation. Both are required.
  • Destination schemes: HTTP, HTTPS, and other destination schemes are accepted globally; browser-executable schemes remain blocked.
  • Recoverability: link deletion is soft deletion, every change stores an immutable snapshot, and restoration appends a new revision.
  • Libraries: Gin, go-oidc/x/oauth2, SCS with a sqlc store, modernc SQLite, sqlc, Goose, log/slog, Prometheus client_golang, and Fuse.js.
  • Deployment identity automation: Ansible defines the Tinyauth OIDC client, authoritatively manages configured members of the Pocket ID start-admins group, and provisions the DNS/ACME records; Start is not double-wrapped with forward-auth.
  • Service integration: the app links to Stirling and other services; it does not provision them.
  • Offline assets: icon/font resources are bundled rather than loaded from public CDNs.

Non-blocking items before first release

  • Confirm the source-control namespace/module path and project license; neither blocks local foundation work.
  • Populate application-specific role/team mappings beyond the decided start-admins bootstrap group as real teams are onboarded.
  • Define and privacy-review the later VPN/network-status heuristic; it remains explicitly outside v1.
